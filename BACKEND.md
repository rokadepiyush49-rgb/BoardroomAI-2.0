# Backend

The backend is **built and wired**. Every screen reads live data from
Supabase, and the board's debate, verdict and deliverables are generated by
Groq. There is no mock data left behind any app route.

## Setup

### 1. Environment

Copy `.env.example` to `.env.local` and fill in:

| Variable | Required | Purpose |
|---|---|---|
| `GROQ_API_KEY` | yes | Every executive persona, the report, and the deliverables. Get one at [console.groq.com/keys](https://console.groq.com/keys). |
| `GROQ_MODEL` | no | Defaults to `openai/gpt-oss-120b`. See "Choosing a model" below. |
| `NEXT_PUBLIC_SUPABASE_URL` | yes | Supabase project URL. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | yes | Supabase anon/publishable key. Never the service-role key. |
| `BLOB_READ_WRITE_TOKEN` | no | Only if you add deck uploads to `POST /api/pitches`. |

`GROQ_API_KEY` is read only through `lib/server/env.ts`, which throws with
a clear message if it is missing. `isAiConfigured()` is the non-throwing
check that route handlers use to return a 503 instead of a 500.

A declared-but-blank variable is treated as absent, so a copied
`GROQ_MODEL=` line cannot silently override the default with an empty
string — which is exactly how an earlier blank model name produced a 404.

### 2. Database

Run both migrations in order (`supabase db push`, or paste into the SQL
editor):

```
supabase/migrations/202607260001_initial_schema.sql
supabase/migrations/202607260002_workspace_data.sql
```

Tables: `profiles`, `meetings`, `meeting_executives`, `messages`, `votes`,
`reports`, `workspace_data`, `activity_events`. Every user-owned table has
row-level security keyed on
`auth.uid()`, so the anon key is safe in the browser — a user can only ever
read their own rows.

### 3. Auth

Email/password plus Google and GitHub OAuth, via `@supabase/ssr`. Enable the
providers you want in the Supabase dashboard and set the callback to
`/auth/callback`. `proxy.ts` (Next 16's middleware) redirects unauthenticated
users away from every app route to `/login?next=…`.

## How a session works

```
POST /api/pitches               → creates the meeting, seats executives, logs activity
  ↓ client redirects to /boardroom?meeting=<id>
POST /api/meetings/[id]/debate  → one executive turn, called repeatedly
  ↓ repeats until isComplete
POST /api/meetings/[id]/finalize → votes + report + deliverables, marks completed
  ↓
/reports/[reportId]             → the generated report
```

`features/boardroom/components/boardroom-session.tsx` drives that loop from
the client, one turn at a time, so the founder watches each executive arrive
instead of waiting on one long request. The founder can interject at any
point; their reply is persisted first, then handed to the next speaker.

Turn-taking lives in **`lib/ai/debate-policy.ts`** — deliberately free of
server-only imports so the UI and the route handler apply identical rules.
Each seated executive speaks `ROUNDS_PER_EXECUTIVE` (2) times: round one is
first reactions, round two is pushback. Change that constant to make sessions
longer or shorter.

## The AI layer

| File | Responsibility |
|---|---|
| `lib/ai/groq.ts` | The only file that talks to Groq. `generateText` for prose, `generateJson` for schema-constrained output. Plain `fetch` — no SDK. |
| `lib/ai/executives.ts` | The eight personas' system prompts. Edit these to change how an agent argues; nothing else needs to change. |
| `lib/ai/debate-policy.ts` | Pure turn-taking rules, shared by client and server. |
| `lib/ai/board-orchestrator.ts` | Builds a persona's prompt from the transcript and produces one transcript message. |
| `lib/ai/report-generator.ts` | The verdict: per-executive votes plus the full `ReportDetail`. |
| `lib/ai/deliverables.ts` | Market research, financials, health snapshot, PRD and pitch deck. |

**Everything the model returns is normalised before it leaves those last two
files.** The report and health screens index into lookup tables by SWOT
title, verdict, severity and risk level, so an off-schema string would crash
a page rather than degrade. The `normalise*` helpers are what make that safe
— keep them if you change the prompts.

### Choosing a model

`lib/ai/groq.ts` asks for structured output two ways, in order:

1. `response_format: { type: "json_schema", strict: true }` — the model
   validates against the schema itself. This is what keeps `enum` fields
   (verdicts, vote ids, severities) honest, and it is the preferred path.
2. If the model rejects that with a 400, it retries once with
   `response_format: { type: "json_object" }` and the schema embedded in the
   system prompt.

Only some Groq models accept `json_schema`, so the fallback means any chat
model works — but the schema-capable ones give noticeably more reliable
reports. If enum drift shows up in reports, pin a schema-capable model via
`GROQ_MODEL` (`openai/gpt-oss-120b`, `moonshotai/kimi-k2-instruct-0905`).
`GET https://api.groq.com/openai/v1/models` lists what your key can reach.

Groq's current chat models reason before answering, and those hidden
reasoning tokens are billed against the same `max_completion_tokens` budget
as the visible reply. A debate turn is capped at 180-260 tokens, which a
default-effort model spends entirely on thinking — the reply arrives with
empty `content` and `finish_reason: "length"`. Every request therefore sends
`reasoning_effort: "low"`; `post()` drops the field and re-sends once if the
pinned model rejects it.

Schemas are authored as plain JSON Schema. `toStrictSchema()` adds
`additionalProperties: false` and fills `required` on every nested object,
since Groq's strict mode demands both — doing it programmatically means it
cannot be forgotten on a nested object.

## Server layer

Route handlers never touch Supabase or Groq directly — they call
`lib/server/*`:

| File | Responsibility |
|---|---|
| `auth.ts` | `requireUser()` — every handler's first line. |
| `meetings.ts` | Create/read meetings, append transcript messages, record votes, complete. |
| `reports.ts` | List/read/create reports. Formats `generatedAt` for display. |
| `board-session.ts` | `finalizeMeeting()` — the whole close-out sequence. |
| `dashboard.ts` | Dashboard metrics and recent meetings, derived from reports. |
| `workspace.ts` | `workspace_data` and profile reads/writes; seeds a workspace on first access. |
| `history.ts`, `executives.ts`, `activity.ts` | Timeline, roster, activity feed. |

`finalizeMeeting()` writes the report and votes **before** attempting
deliverables. If deliverable generation fails, the session still completes
with its report and the previous deliverables stay in place —
`deliverablesRefreshed: false` reports that back.

## API

```
GET  /api/health                    → { status, dbConfigured, aiConfigured, timestamp }
POST /api/pitches                   → create a meeting, seat executives
GET  /api/meetings/latest           → newest/unfinished session, or { meeting: null }
GET  /api/meetings/[id]             → session state + transcript + votes + reportId
POST /api/meetings/[id]/debate      → advance one executive turn
POST /api/meetings/[id]/finalize    → votes, report, deliverables (idempotent)
GET  /api/reports                   → list
GET  /api/reports/[id]              → full report detail
GET  /api/executives                → roster
GET  /api/history                   → version timeline
GET  /api/dashboard                 → metrics, recent meetings, activity, score trend
GET  /api/boardroom/history          → past sessions for the sidebar
GET  /api/workspace                 → profile, workspace deliverables, plan
PATCH /api/workspace                → update profile and notification prefs
```

Every route except `/api/health` requires a session. Request/response shapes
live in `types/api.ts` — change a field there and both the handler and the
consuming `service.ts` get a type error rather than a silent mismatch.

Error codes a client can branch on: `UNAUTHORIZED`, `NOT_FOUND`,
`INVALID_INPUT`, `SUPABASE_NOT_CONFIGURED`, `AI_NOT_CONFIGURED` (503, key
missing), `AI_REQUEST_FAILED` (502, upstream model call failed).

## Where data comes from, per screen

| Screen | Source |
|---|---|
| `/dashboard` | `/api/dashboard` — derived from `meetings` + `reports` + `activity_events` |
| `/boardroom` | `/api/meetings/*` — live session |
| `/meeting/new` | `POST /api/pitches`, roster from `/api/executives` |
| `/reports`, `/reports/[id]` | `/api/reports` — written by `finalizeMeeting()` |
| `/market-research`, `/financials`, `/startup-health`, `/prd-generator`, `/pitch-deck`, `/kanban` | `/api/workspace` — generated by `lib/ai/deliverables.ts` |
| `/executives` | `/api/executives` |
| `/history` | `/api/history` |
| `/settings` | `/api/workspace` (GET + PATCH) |
| `/` , `/pricing`, `/about` | Static marketing copy in `features/landing/mock.ts` — intentionally not backed by a database |

A brand-new user gets a seeded workspace on first access
(`lib/server/workspace-defaults.ts`) so no screen is empty before their first
session. Running a session overwrites those defaults with content generated
from their own pitch.

## Notes and limitations

- **Cost**: a full session is `seats × 2` Groq calls for the debate plus 2
  for the close-out — 18 calls with all eight executives seated. Lower
  `ROUNDS_PER_EXECUTIVE` or seat fewer executives to cut that.
- Deck upload on `/meeting/new` is still a non-functional button; wire it to
  an object store and pass the URL through `POST /api/pitches`.
- Billing on `/settings` is display-only; those buttons are disabled.
- `/kanban` renders from `workspace_data.kanban` but has no drag-and-drop
  persistence yet.
- `react-hooks/set-state-in-effect` is set to `warn` in `eslint.config.mjs`.
  Client data loading here is `useEffect` + `fetch` + `setState`; making it an
  error would require a query library or `use()` + Suspense throughout.
